## [1.0.6] - 2026-11-11

### Added

- `pr-build.yml` reusable workflow: runs `npm ci` and the project build on pull requests, then fails if the expected build output is missing
  - Inputs: `node-version-file`, `node-version`, `build-command`, `output-paths`
  - Repositories without `package.json` pass with a notice, so PHP-only themes and plugins can use the same caller
  - Fails with a clear error when `package.json` exists without `package-lock.json`
- Automated releases with release-please (`release.yml`, `release-please-config.json`, `.release-please-manifest.json`, `version.txt`). Merging the release pull request tags the release, publishes a GitHub Release, updates this changelog, and moves the major tag
- `renovate.json` so Renovate keeps this repository's action versions current. Action updates are titled `fix(deps):` so they ship as patch releases
- README workflow overview, explaining which workflows are called from other projects

### Changed

- **Renamed** `reusable-renovate-clickup.yml` to `renovate-clickup.yml`. Shared workflows now use the same filename as the caller file each project adds. See [Upgrade Guides](#upgrading-to-v106)
- ClickUp lists created by `renovate-clickup.yml` are colored orange
- README versioning notes cover every workflow in the repository, and examples no longer name a specific release

### Removed

- `update-major-tag.yml`. Moving the major tag is now part of `release.yml`, which also handles tags pushed by hand

## [1.0.5] - 2026-11-11

### Added

- `reusable-renovate-clickup.yml` reusable workflow: mirrors Renovate pull requests into ClickUp tasks
  - Routes each repository through the `clickup_space` or `clickup_list_id` organization custom property
  - Finds or creates a `Dependency Updates` list in the space
  - Creates, renames, reopens, and closes tasks as the pull request changes
  - Inputs: `list-name`, `bot-login`, `tags`, `priority`
- `update-major-tag.yml`: moves the major tag (e.g. `v1`) to each new full version tag
- README documentation for the ClickUp workflow

## [1.0.1] - 2026-01-26

### Added

- `WP_CONTENT_PATH` values that contain `wp-content` anywhere in the path resolve correctly

## [1.0.0] - 2026-01-26

### Added

- Initial release of the reusable WordPress deploy workflow
- Multi-job workflow with lint, deploy, and notify stages
- PHP CodeSniffer linting with WordPress Coding Standards
- SSH-based deployment via rsync
- Support for multiple project types:
  - Themes (`themes/`)
  - Plugins (`plugins/`)
  - MU-Plugins (`mu-plugins/`)
- Multi-host cache clearing support:
  - Kinsta (`wp kinsta cache purge`)
  - WP Engine (`wp engine cache flush`)
  - Pressable (`wp pressable cache purge`)
  - Generic (`wp cache flush`)
- Per-project configuration via `wp-deploy-config.yml`
- Configurable exclude patterns for rsync
- Slack notifications for deployment status
- Environment-based deployments (development, staging, production)
- Branch-to-environment mapping (main→production, staging→staging, develop→development)
- Manual deployment trigger via `workflow_dispatch`
- Configurable PHP version for linting
- Support for both repository variables and secrets for SSH configuration

## Upgrade Guides

### Upgrading to v1.0.6

The ClickUp workflow was renamed. Once `v1` points at `v1.0.6`, a caller still using the old filename fails. Update the `uses:` line in each project's `.github/workflows/renovate-clickup.yml`:

```yaml
# Before
uses: dev-hero/reusable-wp-deploy/.github/workflows/reusable-renovate-clickup.yml@v1

# After
uses: dev-hero/reusable-wp-deploy/.github/workflows/renovate-clickup.yml@v1
```

Callers pinned to `@v1.0.5` keep working until they move to a newer tag.

### Migrating from Inline Workflow to v1.0.0

If you're migrating from a standalone workflow in your project:

1. **Remove** your existing `.github/workflows/deploy.yml` (or similar)

2. **Create** a new minimal caller workflow:

   ```yaml
   name: 'Deploy'

   on:
     push:
       branches: [main, staging, develop]
     workflow_dispatch:
       inputs:
         environment:
           description: 'Environment to deploy to'
           required: true
           type: choice
           options:
             - development
             - staging
             - production

   jobs:
     deploy:
       uses: dev-hero/reusable-wp-deploy/.github/workflows/wordpress-deploy.yml@v1
       with:
         environment: ${{ github.event.inputs.environment || (github.ref_name == 'main' && 'production') || (github.ref_name == 'staging' && 'staging') || 'development' }}
       secrets: inherit
   ```

3. **Ensure** your `wp-deploy-config.yml` exists and is properly configured

4. **Verify** all required secrets are set in your repository
